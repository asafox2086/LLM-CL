**端侧需存多少适配权重？** 按当前全量配置的未合并 FP32 张量计，共享 q/v LoRA 与八专家 CL-MoE 在 OneVision 上分别新增 **2.16／148.64 MB**，在 Qwen 上分别新增 **4.36／311.72 MB**。两个基座上，路由器均只占八专家新增权重的约 5.2%–5.3%。主要开销来自 LoRA 同时覆盖七类投影，并将每层总秩从 8 提高到 64。OneVision 保持七类投影和总秩 64，将架构从八个秩 8 专家改为一个秩 64 专家，LoRA 因子仍占 140.77 MB，总量降至 141.75 MB，仅少 4.63%。这里按十进制 MB 统计新增模型参数，任务统计和文件封装另计。[逐投影层字节核算](summary/image_disjoint_adapter_bytes_20261119/ADAPTER_BYTES.json)

**设备上需要多存多少权重？** 若只保留一个专用的 FP16 模型，共享 LoRA 和固定组合的八专家都可以把更新写入基座，两者的部署权重净增均为 **0 MB**。若保留一份基座、另存可切换的 FP32 适配器，OneVision 的共享 LoRA 需 **2.16 MB**，固定八专家的完整因子需 **140.77 MB**。在已有的 1%／10% OneVision 检查点上，八专家的 168 个固定更新写回 FP16 时，舍入误差平方和分别占更新平方和的 **1.56%／0.19%**。将每层固定更新截成秩 8，适配器减至 **17.60 MB**，对应的更新平方误差占 **40.90%／37.54%**。按层选秩、各保留至少 95% 的更新平方和，需 92.74／85.31 MB。写回与截断对完整测试 F1 的影响待测。[FP16 写回测量](summary/parameter_efficiency_retention_20261118/FIXED_DENSE_FP16_SUMMARY.json) · [各层秩与存储量](summary/parameter_efficiency_retention_20261118/FIXED_EXPERT_RANK_SUMMARY.json)

**端侧继续学习还要保留什么？** PaRSP 每个任务结束后为各层保存输入特征的二阶矩，后续任务用它约束梯度。第一项任务完成后，OneVision 和 Qwen 的这部分 CPU 内存就分别为 **2.50 GB 和 9.78 GB**。其中 90.8% 和 91.9% 用在前馈网络的降维投影，因为每层保存的是输入宽度平方大小的 FP32 矩阵。后续阶段把当前统计加进同一组历史矩阵，历史占用随模型宽度变化，不随任务数累加。仅推理时无需保留这组训练状态。

**全量训练的同题耗时与显存。** OneVision 第一项任务的学习率预热共 64 次更新。相同的 1,024 道训练题上，共享 LoRA 用时 **12.08 分钟**，八专家用时 **73.72 分钟**，前者少用 **83.6%**。同一预热段，框架实际分配的 GPU 显存峰值分别为 **2.51／7.33 GB**；第 64 步结束时分别为 **1.87／2.46 GB**。逐步核对了输入与答案 token 数；两次运行在同机不同 RTX 2080 Ti 上，并发负载未控制。此处只计预热段的主训练更新。[配对计时](summary/image_disjoint_adapter_bytes_20261119/WARMUP_TIME.json)

**全量持续学习的阶段末开销。** 八专家 CL-MoE 在 19 个任务结束时统计路由权重，按全量训练清单合计需要 **129,460 次图文前向**。检索历史任务还需 **57,264–59,409 次纯文本前向**，具体次数取决于每个阶段开始统计时缓存了哪些题干。Qwen 八专家在首个 TextVQA 任务上完成 2,163 次参数更新用了 **25.86 小时**。最后一次更新后，阶段末统计等处理又用了 **7.68 小时**，占评估前总用时 **33.55 小时的 22.9%**。共享 LoRA 省去两项路由统计。等总秩单专家对照沿用相同的统计流程，但它的门权重恒为 1，从第二个任务起固定保留 70% 的上一阶段 LoRA 因子和 30% 的当前因子。归档模型 168 个投影、19 个阶段的 3,192 个历史权重全部为 1。因此单专家可以直接计算阶段合并，省去上述统计前向；全量训练实际能节省多少时间待测。[Qwen 首任务分段计时](summary/rgb_stage_end_work_20261119/FULL_T01_QWEN_EIGHT_STAGE_COST.json)

**全量训练中，少参数是否已经减少更新耗时？** OneVision 的首个 TextVQA 任务中，两种方法按相同顺序训练前 8,192 题，逐步核对了输入和答案词元数以及视觉缓存命中。512 次主更新中，共享 LoRA 累计用时 **1.60 小时**，八专家 CL-MoE 用时 **9.75 小时**。分为四个连续的 128 步区间，八专家每段均耗时约 **6.1 倍**。两种方法使用同机不同的 RTX 2080 Ti，机器并发负载未控制。共享 LoRA 完成首任务全部 34,602 题、2,163 次主更新共用 **6.77 小时**，更新期间 PyTorch 实际分配的显存峰值为 **2.51 GB**。八专家完整首任务耗时与两种方法的序列末 F1 待核验。[配对训练日志摘要](summary/rgb_stage_end_work_20261119/FULL_T01_FIRST512_TIME.json) · [共享 LoRA 完整首任务日志摘要](summary/rgb_stage_end_work_20261119/FULL_T01_SHARED_COST.json)

**路由权重集中时，能否少算几个专家？** 在两个正式基座的训练前向中，将一个专家的权重设为 99.97%，其余七个仍全部执行。共享 LoRA 只覆盖查询和值两类投影；八专家覆盖七类，每类执行八条低秩路径。因此每次解码器前向，OneVision 的低秩路径从 48 条增至 1,344 条，Qwen 从 56 条增至 1,568 条，均为 **28 倍**。路由在八条路径算完后对输出加权，高权重集中本身不会节省专家计算。该计数来自正式代码的合成输入；尚未分解各部分对实测训练耗时的贡献。[逐投影调用计数](summary/rgb_stage_end_work_20261119/FULL_EXPERT_FORWARD_WORK.json)

**总秩相同，训练八个专家还多存什么？** 一个秩 64 专家和八个秩 8 专家覆盖相同的七类投影，LoRA 系数一样多。按每个输入 token 汇总各投影为反向传播保存的非参数张量，单专家／八专家在 OneVision 上为 **4.21／26.49 MB**，在 Qwen 上为 **8.74／55.31 MB**。该实现对八条路径分别执行 dropout。逐张量核对发现，两种基座增加的保存量中，**61.8%／61.2%** 来自各路径的 dropout 掩码及处理后的输入，**38.2%／38.8%** 来自为计算门权重梯度而保留的各专家输出；门权重数值本身均不足 **0.03%**。这是 CPU 上按各投影累加的反向保存量，整模型 GPU 峰值与等总秩训练耗时待实测。[等总秩反向传播测量](summary/rgb_stage_end_work_20261119/EQUAL_RANK_ACTIVATIONS.json) · [按张量来源分解](summary/rgb_stage_end_work_20261119/EQUAL_RANK_ACTIVATION_ROLES.json)
