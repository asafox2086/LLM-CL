# 架构扩展必要性：分工、容量和部署是否得到相称收益

## 实验意义（启动前）

**问题。** 在冻结1%持续学习中，原架构的多专家分工和较大的适配总rank，是否各自带来足够收益？用户要求查明哪些扩展可以避免，而不是先认定它们无用。

**证据。** CL-MoE／SMoLoRA作者类把总rank分配给专家；当前端口分别固定8专家、总rank64／128。减少专家数但保总rank不会相应减少A/B参数。两者并非每阶段新增专家。此前冷启动局部证据不能解释所有MoE，也没有完整删减对照。本实验不依赖CPU量化负例或视觉占比，直接检验论文中的专家化机制。

**有区分力的对照。** 各方法三条件：原配置；减少分工但保持总rank；减少分工且减小总rank。前两者区分“专家化”与适配参数预算，后两者检验共享时的大rank是否必要。位置、基座、原生任务顺序、QA、主更新、学习率、缩放及其他作者机制保持。SMo至少保留视觉与指令两个分支，不能将2专家条件声称单分支。

**正结果用途。** 若较少分工／小rank在完整五域质量不劣且成本明显降低，可避免该扩展；再考察统一的容量配置原则，而不包装为单篇论文实现优化。领域宏观收益为准，不要求每个小类上涨。原始rank小于共享rank的比较不能单独解释成冷启动原因。

**负结果用途。** 若删减显著损害最终质量，保留对应结构；若质量保住但完整部署成本只微变，则否定“只砍适配器就足够解决端侧部署”的路线。OSFT常规静态模型没有常驻专家，减少MoE开销不能自动算击败最强OSFT的端侧开销；最终目标仍需更强证据。

**成本与出口。** 六组各1313TRAIN／19阶段／93主更新；先做全部六组训练，再全部六组21454最终测试，共128724最终QA，不以测试分数删条件。原CL另有作者当前TRAIN统计前向与问题特征计算，单列计费。不开初始和中间TEST，从而此轮不发布完整FWT/BWT，不回填未来权重。先行19条TRAIN探针仅检查恢复和习得，不能替代完整质量。旧GPU1作业和全部已准入确认义务保留。

## 训练、资源与质量口径

基座OneVision0.5B，正式公共401408输入与128MiB冻结视觉cache；CL按作者端口FP16基座／FP32适配，SMo按作者native BF16基座／FP32适配。只在各自家族内部做配对，不能把跨精度差当作容量因果。相同原1313 ID、19任务顺序、batch16/micro1、1epoch、原有效floor warmup／cosine及实际93正LR更新，原clip1和优化器规则不变。各阶段沿用全部当前参数，不逐任务新建或清零。

原型保存每阶段loss／实际LR／逐模块原始梯度统计、每阶段首更新完整原始梯度、参数变化／实际结构、同PID CPU RSS/PSS/USS与GPUallocated/reserved/NVML前后／TRAIN峰值；采集开销计入。不声称保存了每一步完整梯度张量。只保最新阶段与最终适配器状态和必要CL锚／路由统计，保存源／基座文件引用及SHA；独立恢复门槛未通过不得称可恢复。

最终原Answer F1按全部原answers计算；各域报告完整题数和F1／AP。计实际部署包（含基座、视觉、投影、router、专家）、CPU/GPU峰值、TTFT和tok/s。同一设备／输入／格式／精度下比较，常规合并折叠对各方法公平。GPU1时序／资源必须无其他作业竞争才用于正式部署比较，服务器不是手机。
