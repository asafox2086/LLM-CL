# 保护机制是否在极少更新下真正启用？

2026-10-18。这是**冻结V2代码的确定性日程审计＋原作者算子的微型CPU正负对照**，不是新增GPU性能实验。唯一主指标仍为原始Answer F1；没有读取TEST、改变数据或热改任何活动/排队源码。

| 项目 | 记录 |
| --- | --- |
| 探究的问题 | 正则化可以很轻量，但在每个任务只有一两次更新时，它是否真的参与了优化？不能只因方法名包含保护，就假定保护已经生效。 |
| 做的实验 | 核验两机相同的V2调用代码、冻结1313条TRAIN和19阶段；追踪PASs-MoE作者的任务进度预热与post_backward。用当前适配器加载并校验原作者算子，在4维CPU小模块中人为设置非零参数距离和非空旧重要性，分别给进度0/.15/.3及关闭预热四个条件；不执行优化器更新。 |
| 结果 | 19阶段共93次优化器更新；9个阶段只有一步，其整个阶段传入的进度始终为0，故该二次保护项的有效系数必为0。CPU对照中新增正则梯度范数依次为0、1.0879298351e-5、2.1758596702e-5、2.1758596702e-5；参数本身全部未变。 |
| 证明了什么 | 已验证：在当前极少更新协议中，保护预热可能持续到任务结束，导致这个具体正则项没有启用。它与“最新中心处二次惩罚首梯度为0”是不同限制：本对照故意令参数不在中心，进度0仍直接使系数归零。没有证明这造成最终F1下降、PASs整体无效或正则化不适合小数据。 |
| 改进的方法 | 比较保护机制前，核对真实附加梯度和启用时机；未来保护模块对照必须区分原始预热、有效启用与同预算无保护。这里只记录待验证条件，不更改当前正式PASs或增开重复GPU队列；原48组机制控制继续。 |
| 改进的效果 | 尚无新的模型性能收益或内存优势。当前完成的是机制生效条件的证据，不将CPU梯度控制冒充Answer F1改进。 |

## 1. 九个阶段具体是哪几个？

| 阶段 | TRAIN QA | 优化器更新数 | 传入进度 | 该项预热系数 |
| --- | ---: | ---: | ---: | ---: |
| T02 Modality | 11 | 1 | 0 | 0 |
| T05 Size | 6 | 1 | 0 | 0 |
| T06 Abnormality | 14 | 1 | 0 | 0 |
| T07 Quantity | 4 | 1 | 0 | 0 |
| T08 Plane | 5 | 1 | 0 | 0 |
| T09 Shape | 1 | 1 | 0 | 0 |
| T10 Color | 3 | 1 | 0 | 0 |
| T11 KG | 12 | 1 | 0 | 0 |
| T12 rural_urban | 6 | 1 | 0 | 0 |

任务名称以原manifest为准；没有根据答案重新划分。其他10个阶段的**第一批**系数也为0，后续更新可能启用。是否有旧重要性、参数距离、梯度路径还会影响实际作用，不能从非零系数直接断言非零保护梯度。

当前V2在每批样本逐条反向时传入同一个`start / len(order)`。作者默认`reg_warmup_ratio=.3`，令：

`lambda_eff = lambda_stab * min(1, task_progress / .3)`

当只有一个批次时，`start=0`；即使它包含多个逐条反向调用，传入进度仍全部为0。这里归零的是**附加正则系数**，不是任务学习率或任务梯度。真实任务仍可以学习，不能与旧Qwen零学习率问题混为一谈。

## 2. 作者原设计还是我们的框架问题？

作者固定版本`eb0d571173fcaa21db5f7231d63a64f0db7529c8`的`llava/train/llava_trainer.py:478—490`，同样用`state.epoch / num_train_epochs`将任务进度传给`post_backward`；原learner自身实现30%进度预热。文件SHA已与下载时原始清单一致：`88fac2d65a3f2ee4aa2ec6e97c8009acdfc245d011349b2251f496fdf6d0d728`。

安装的Transformers 4.46.3源码也显示：训练开始先置epoch=0，调用training_step后才更新epoch。本审计没有运行作者完整Trainer、DeepSpeed或对齐全部梯度累积行为，因此**不声称已证明整个适配框架与作者训练逐步等价**。可以确认的是：预热规则来自作者代码；当前冻结调用方式在单步阶段会遇到零系数边界。不能把它直接定性为我们写错算法或作者算法错误。

两机当前`run.py`、`pass_adapter.py`与原learner SHA逐一相同；旧机PASs PID342152/startticks692346567实际存活。当前源码与运行参数均未改动。将来若改变预热，应作为明确标注的新消融，不能悄悄覆盖原基线。

## 3. 正负对照究竟排除了什么？

微型CPU对照不是在`theta=theta_ref`处测试：A/B参考均人为偏移0.25；旧重要性非空、梯度张量存在、lambda=1e-4，B权重系数=.1、top-p=.4沿用当前配置。

- 进度0、保留预热：新增梯度严格为0。
- 进度.15/.3：新增梯度严格非零，且半预热/全预热范数比例符合公式。
- 进度0、仅去掉预热：新增梯度恢复，与全预热对照相同。
- 所有A/B参数前后精确相同：这里只调用附加梯度算子，没有训练模型。

所以这个零结果不是“没有构造旧中心”“距离恰好为0”或“算子根本未接入”的假阴性。它仍然不是实际OneVision训练中测得的正则梯度日志，更不是启用后能提高性能的证据。

## 4. 与研究主问题的关系

这支持一个具体、可检验的方向：**从大训练预算沿用的保护日程，在极少更新时可能退化为不保护**。因此，现有方法表现不好时，应该先检查关键机制是否参与优化，再讨论多领域冲突或专业知识缺失。

但不能泛化为所有保护方法都存在此问题。PASs其他专家/路由/重要性统计仍可工作；它在已有Organ习得评价中已有明显整体改善，不能用本限制否认已观察到的收益。共享LoRA与正则化可以结合，当前结果没有给出二者哪一种最终更好的答案。
